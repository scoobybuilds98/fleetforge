# FleetForge Audit — Reservations

Date: 2026-05-26
Auditor: Codex
Scope: `app/admin/reservations/`, `api/v1/reservations/`, `cron/stale_reservations.php`, and canonical reservation/equipment status schema. Production code only; skipped vendor/public/tests/db_migrations/docs.
Tables checked: `reservations`, `reservation_units`, `equipment_units`, `equipment_status_log`, `leases`, `customers`, `users`, `user_roles`, `audit_log`, `settings`, `notifications`, `yards`, `equipment_templates`.

## [CRITICAL] — Stale-reservation cron can free a unit from a confirmed reservation
File: cron/stale_reservations.php:101
Code:
```php
db_execute(
    "UPDATE reservations
        SET status         = 'cancelled',
            internal_notes = ?,
            updated_at     = NOW()
      WHERE id = ? AND status = 'pending' AND deleted_at IS NULL",
    [$updatedNotes, $resId]
);
```
Why it's a problem: The cron selects stale pending reservations, then later attempts a conditional update but never checks whether that update affected a row. If a user confirms the reservation after the cron's initial SELECT but before this UPDATE, the UPDATE affects 0 rows, yet the cron continues to inspect linked units and may flip a now-confirmed reservation's reserved unit back to available. That creates a live race where a valid confirmed pickup can lose its unit assignment in operations.
Proposed fix: Process each stale reservation inside a transaction, lock the reservation row with `FOR UPDATE`, re-check `status = 'pending'`, and stop processing if the conditional update affects anything other than one row. Lock unit rows before freeing them.

Why it's a problem: `force_override` comes directly from the request body and is honored for any caller with `reservations:create`. A user or script can skip the conflict response entirely and create a second active reservation on the same equipment unit without an elevated permission, signed override token, or server-side approval record. This weakens the module's core one-active-reservation-per-unit invariant.

## [MEDIUM] — Cancelling a double-booked reservation can release another reservation's unit

```php
    if (!$unitNewStatus) continue;

    if ($unitOldStatus && $u['current_status'] !== $unitOldStatus) {
        // Unit is in an unexpected state — log but don't block the transition
```
Why it's a problem: The cancellation path changes `reserved` units back to `available` based only on the unit's current status. It does not check whether another pending/confirmed reservation still holds the same unit, even though `create.php` can intentionally create that duplicate with `force_override`. Cancelling one reservation can therefore make a unit appear available while another active reservation still depends on it.

## [MEDIUM] — Mark-out can link a reservation to an unrelated lease

```php
if ($leaseId) {
    $lease = db_row(
        "SELECT id, status FROM leases WHERE id = ? AND deleted_at IS NULL",
```

Why it's a problem: The endpoint accepts an optional `lease_id` and validates only that the lease exists. A caller with reservation edit permission can link every unit on this reservation to an unrelated customer's lease, a lease for a different unit, or a lease in an inappropriate status, then force the reservation units to `on_lease`. ## [MEDIUM] — Reservation optimistic lock is checked before the transaction but not enforced by the write
File: api/v1/reservations/update.php:73
Code:
```php
if (!optimistic_lock_matches($submittedAt, $existing['updated_at'])) {
    json_error('STALE_DATA',
        'This reservation was modified by another user. Refresh and try again.', 409,
        ['fields' => ['updated_at' => 'This reservation was modified by another user. Refresh and try again.']]);
}
```
Why it's a problem: The stale-token and immutable-status checks run before the transaction, but the final update writes by `id` only. A concurrent status change or edit can land after this check and before the update, allowing a stale request to overwrite reservation metadata or edit a reservation that just became cancelled/completed. The optimistic lock is therefore advisory rather than enforced at the mutation point.
Proposed fix: Re-read the reservation row `FOR UPDATE` inside the transaction and compare `updated_at`/status after acquiring the lock, or include `updated_at = ? AND status IN ('pending','confirmed')` in the final update predicate and require exactly one affected row.

## [LOW] — Reservation status logs write user IDs into the free-text attribution column
File: api/v1/reservations/create.php:309
Code:
```php
db_insert('equipment_status_log', [
    'equipment_unit_id' => $unitId,
    'changed_by'        => current_user_id(),
    'old_status'        => $currentStatus,
    'new_status'        => 'reserved',
    'reason'            => "Reservation #{$newId} created as confirmed",
```
Why it's a problem: The canonical `equipment_status_log` schema has `changed_by` as a text label and `changed_by_user_id` as the user FK. Reservation endpoints write the numeric user id into `changed_by` and leave `changed_by_user_id` unset, so status-history joins cannot reliably attribute reservation-driven status changes to a user. The same pattern appears in the reservation create, status-update, delete, and mark-out flows.
Proposed fix: Populate `changed_by_user_id` with `current_user_id()` and keep `changed_by` as a display label such as the user's name or `system`. Update the reservation status-log writers consistently.
